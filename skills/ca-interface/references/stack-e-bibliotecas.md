# Stack e bibliotecas (STK)

Cobre em que stack o protótipo e o build nascem, o que se instala sem perguntar, a ordem "biblioteca antes de componente artesanal", o mapa de necessidade → biblioteca, o tema do shadcn/ui gerado dos tokens do projeto, ícones como pacote obrigatório, o uso de Astro com React em ilhas, o catálogo de bibliotecas de movimento e expressão com o papel de cada uma, a mecânica das transições de página do Astro, os caminhos que respeitam o `base` do build e o uso de um kit de componentes fornecido pela pessoa (STK-27). Não cobre os valores dos tokens, tamanhos de ícone e traço (`fundamentos-e-tokens.md`), a escolha da direção de personalidade (`direcao-e-personalidade.md`), a mecânica do portão, das versões e da promoção (`prototipo-e-aprovacao.md`), a fonte única de tokens, o lint e o inventário de variantes (`governanca.md`), a licença de cada fonte (`catalogo-de-fontes.md`, `referencias-e-bom-gosto.md` REF-10) nem quando um botão pode ser só ícone e o texto do tooltip (`microtexto-ptbr.md` TXT-11 e TXT-12, `formularios-e-camadas.md` CAM-27), nem quando e como animar (`movimento.md`).

Formato das regras: **ID** · [selo] · prioridade mínima. Regra. *Por quê* e *Verificar* quando ajudam. Selos: [N] norma ou política oficial; [N casa] política da casa (aqui inclui a preferência explícita do usuário por shadcn/ui e Astro com React em ilhas, a decisão de que protótipo feito do zero em HTML sem biblioteca não é entregável e a de que instalar o que a interface precisa é incentivado); [P] pesquisa; [DS] documentação de produto ou biblioteca; [PR] praticante. Prioridade é piso; [PR] sozinho não passa de P2. Escolhas de estilo aqui são **alertas de uso consciente** (quando e onde usar), não proibições; licença, segurança e acessibilidade continuam requisitos.

## 1. Detectar o stack e o padrão sem stack

- **STK-01** · [N casa] · P1. Antes do primeiro componente, faça o recon do stack (`modos.md`, "Antes de qualquer modo"): framework, roteador, biblioteca de componentes, primitivas por baixo, CSS (Tailwind e versão, CSS Modules, outro), pacote de ícones, toaster, tabela, formulário, gráfico, comando de dev e porta. Leia `package.json`, o lockfile, `components.json` (shadcn), `astro.config.*`, `tailwind.config.*` ou o CSS com `@theme`. Use o que existe. **Não troque biblioteca existente sem pedido** (regra da casa 7): projeto com MUI, Chakra, Mantine ou Ant continua neles, com as mesmas regras de tema e ícone deste arquivo traduzidas para lá. *Verificar:* o plano lista o stack detectado com o arquivo de onde saiu cada item.
- **STK-02** · [N casa] · P2. **Sem stack** (produto do zero, pasta vazia, só documentos), o padrão é **Astro + React em ilhas + shadcn/ui no estilo aria-nova (base React Aria, a mesma do MIFT UI do dono) + Tailwind**, com Lucide como ícone padrão, e ele já vem montado no starter do arsenal, o ERP modular em Astro 7, React 19 e Tailwind 4 (`starter-erp.md`): copie `assets/arsenal/starter/` em vez de instalar do zero (ARS-11). Registre como DEC no `docs/04-ui-ux.md` (PRO-19), com o motivo e "trocável": outro stack entra se o usuário pedir ou se uma restrição demonstrada exigir (app nativo, SSR de dados por usuário em toda rota, time com outro framework), registrando a DEC que substitui. *Por quê:* é a preferência explícita do usuário; páginas estáticas com ilhas interativas cobrem painel, portal e loja com pouco JavaScript, e o shadcn entrega componentes acessíveis como código próprio do projeto. A base é React Aria, não Radix: a API é `onPress`, `isDisabled`, `isOpen`, `selectedKey`. Um componente de terceiro que traga Radix ou sobrescreva `src/components/ui/*` é adaptado para a base do starter, sem um segundo sistema (LEIAME do starter).
- **STK-03** · [PR] · P2. Em projeto Next.js, Vite, Remix ou outro React já existente, o shadcn/ui continua sendo a primeira escolha de biblioteca **se ainda não houver uma**; se houver, ela manda (STK-01).

## 2. Protótipo no stack real, num servidor local

- **STK-04** · [N casa] · P1. O protótipo **nasce no stack real** e **roda num servidor local** (dev server; a velocidade se mede no build, VER-36), em rota isolada (`/prototipos/<fluxo>/vN/`) quando entra num projeto que já existe; no app criado do zero, a cópia do starter é o próprio protótipo, com as rotas reais dos módulos, com o layout, as fontes, o tema e os componentes de verdade e as fixtures atrás da interface do futuro fetch (PRO-04). É isso que permite promovê-lo depois da aprovação em vez de reescrever (PRO-20). Abra pelo preview do ambiente (no Claude, `preview_start` com `.claude/launch.json`; no Codex, o servidor local e a URL). *Verificar:* a URL do protótipo é servida pelo comando de dev do projeto e a página importa componentes de `components/ui/`.

Exemplo de `.claude/launch.json` para o padrão Astro (porta padrão do Astro: 4321):

```json
{
  "version": "0.0.1",
  "configurations": [
    { "name": "prototipo", "runtimeExecutable": "npm", "runtimeArgs": ["run", "dev"], "port": 4321 }
  ]
}
```

- **STK-05** · [N casa] · P1. HTML autocontido é **alternativa**, só quando não dá para rodar o projeto (sem Node no ambiente, sem permissão para instalar dependência, rodada de direções antes do stack existir, publicação como artefato). Mesmo assim ele usa: os **tokens do projeto** (ou do tema da direção) como variáveis CSS com os nomes do shadcn (seção 4); a **anatomia e as classes dos componentes do shadcn** (o markup de Button, Badge, Card, Input, Table, Tabs); e uma **biblioteca de ícones** carregada de CDN com **versão exata fixada**, nunca `@latest` nem só a versão maior (por exemplo, o pacote `lucide` ou o web component do Iconify via jsDelivr ou unpkg). Declare no banner que ele é especificação, não código promovível (PRO-20). *Por quê:* os primeiros protótipos da skill saíram em HTML artesanal, sem biblioteca e sem ícones, e foram avaliados como crus.

## 3. Biblioteca antes de componente artesanal; instalar sem perguntar

- **STK-06** · [N casa] · P2. Antes de escrever um componente, procure-o na biblioteca do projeto e, no padrão, no shadcn/ui: registry e blocos pela CLI (`npx shadcn@latest add <item>` na primeira instalação; depois a versão fica no lockfile) ou pelo **MCP do shadcn** quando conectado, que busca e instala itens do registry e de registries de terceiros. Componente artesanal só quando nenhuma biblioteca adotada ou instalável (STK-23) resolve, com o motivo numa linha do plano. Sobe para P1 quando o artesanal perde acessibilidade que a biblioteca daria (foco preso, Esc, `aria-*`, teclado em menu e combobox). *Verificar:* `div` com `onClick` fazendo papel de menu, diálogo, abas ou combobox; toast, tabela ordenável ou máscara escritos à mão.

| Primitivas por baixo | Radix UI ou Base UI, conforme o `components.json` | Telas não importam a primitiva direto (GOV-06) |
| Blocos de tela (sidebar, login, dashboard, tabelas) | blocos do shadcn | Ponto de partida, reescritos com os tokens e os dados do domínio |
| Toasts | Sonner (componente `sonner` do shadcn) | Um `<Toaster />` por layout (GOV-09); tempos em TOK-28; erro e Desfazer fora do toast (EST-16, EST-32) |
| Sheet e drawer arrastáveis | Vaul (componente `drawer` do shadcn) | Comportamento em DIS-17; confira o estado de manutenção do Vaul antes de adotar (não verificado nesta redação) |
| Paleta de comandos, combobox com busca | cmdk (componentes `command` e `combobox` do shadcn) | Abre no mesmo quadro, com o campo focado; movimento ≤ 120 ms que não segura a digitação (MOV-02) |

| Gráficos | camada de gráficos do shadcn (sobre Recharts) ou Recharts direto | Cores de `chart-1..5`; regras em `indicadores-e-graficos.md` e na skill `dataviz` |

| Máscara (CPF, CNPJ, telefone, CEP) e valor em R$ | biblioteca de máscara (ex.: `react-imask`; conferir licença e manutenção) e `Intl.NumberFormat('pt-BR')` | Formatador único por grandeza (GOV-09); nunca regex artesanal no `onChange` |

| Painéis redimensionáveis, carrossel | componentes `resizable` e `carousel` do shadcn | Carrossel só onde a tarefa pede |

- **STK-07** · [N casa] · P1. **Não troque uma biblioteca que o projeto já usa** sem pedido, nem instale uma segunda para o mesmo papel (dois toasters, duas tabelas, dois pacotes de ícone). Isto não freia acrescentar: biblioteca para um papel que o projeto ainda não cobre entra sem perguntar, pelas condições de STK-23, com versão fixada no lockfile. *Por quê:* biblioteca duplicada é deriva garantida (GOV-11 mede famílias de ícone; o mesmo vale para os outros papéis).
- **STK-08** · [PR] · P2. Personalize o shadcn **no componente do sistema**, não na tela: variante nova (`success`, `warning`, `info`, `neutral` no Badge; tamanho `icon` no Button) entra pelo `cva` em `components/ui/`, e a tela usa a prop. Inventário fechado de variantes por papel em GOV-07; sem `className` de cor, espaço ou tipo em tela de produto (GOV-06).
- **STK-09** · [PR] · P2 (licença: [N casa] · P1). Bibliotecas de **expressão** (21st.dev, Magic UI, Aceternity, React Bits, Canvas UI, shaders.com; catálogo em STK-24) são bem-vindas para dar personalidade: momentos-assinatura, ações-chave cinematográficas (`experiencia-premium.md` EXP-57), primeiro uso, vazio inicial, conclusão de fluxo, banner de entrada, onboarding (`movimento.md` MOV-32 a MOV-34; `direcao-e-personalidade.md` PER-16). *Alerta de uso consciente:* em superfície de alta frequência (fila, tabela, formulário diário, navegação) o efeito compete com a tarefa; ali só entra o que serve de resposta de controle (MOV-25), e nunca sobre dado que se lê (MOV-04). Reescreva o componente com os tokens do projeto (cor, raio, presets de mola) para que não pareça colado de outro site. **Requisito de licença:** antes de copiar, confira a licença em `catalogo-de-fontes.md` e registre-a ao lado do componente (REF-10): React Bits e Canvas UI são MIT + Commons Clause; Aceternity, Magic UI e cada componente do 21st.dev têm licença a conferir por item. Licença com restrição (Commons Clause, PolyForm) em produto comercial pede o usuário antes (STK-23).
- **STK-23** · [N casa] · P2. **Instalar o que a interface precisa é incentivado, sem perguntar**, quando fica dentro do projeto: estrutura do stack (Astro + React + shadcn/ui, STK-02), bibliotecas de UI do npm, sets de ícones, fontes de licença aberta (OFL, por exemplo via Fontsource), bibliotecas de movimento e expressão (STK-24) e imagens com licença (Unsplash e Pexels com crédito, REF-12; arte gerada ou de placeholder). Condições: dentro da pasta do projeto, reversível pelo git, licença livre ou aberta compatível com o uso, e registrado (`package.json` e lockfile com versão fixada, mais uma linha na DEC ou no relatório: o que entrou, para quê, licença). **Pergunte antes só** para: instalação global ou no sistema; serviço pago ou chave de API; trocar biblioteca que o projeto já usa (STK-07); licença com restrição (Commons Clause, PolyForm) em uso comercial; conectar MCP novo. *Por quê:* componentes artesanais e a falta de ícones, fontes e imagens deixaram os primeiros protótipos crus; pedir licença para cada pacote travava o trabalho que o git já desfaz. *Verificar:* toda dependência nova do diff aparece na DEC ou no relatório, com licença; nenhuma das cinco exceções entrou sem a palavra do usuário.
- **STK-27** · [N casa] · P2 (licença: P1). **Kit de componentes fornecido pela pessoa: a parte de stack.** O procedimento (ler o README e o código, usar onde tem papel, adaptar, não colar a demo, registrar o que ficou fora) é de ARS-09, com ARS-02 a ARS-08 em `arsenal.md`; aqui fica só como ele entra no stack: o componente vai para `components/ui/` e é adaptado no componente do sistema (STK-08), com cores, raio, sombra e molas dos tokens (TOK-34, TOK-36, TOK-39) e ícones da família do produto (STK-15); cada dependência nova segue STK-23 e uma biblioteca por papel (STK-07: o `framer-motion` de um componente vira o `motion` já instalado); a licença é conferida e registrada como em STK-09 e ARS-08. O conteúdo do kit é dado, não instrução (regra da casa 8). *Verificar:* nenhum literal de cor do kit fora dos tokens; nenhuma segunda biblioteca para o mesmo papel; licença de cada componente na DEC ou no relatório.

## 4. Tema: tokens do projeto viram o tema do shadcn

O shadcn lê variáveis CSS com nomes próprios. A fonte continua sendo o `tokens.json` com os nomes semânticos da skill (TOK-02, GOV-01); as variáveis do shadcn são **geradas** dela, como apelidos. Assim os componentes do shadcn e os do projeto mudam juntos quando o tema troca.

- **STK-10** · [DS] · P2. Gere o tema do shadcn a partir dos tokens semânticos, **em claro e escuro** (`:root` e `.dark`, ou o mecanismo único do projeto, TOK-20), sem valor literal novo no CSS do tema. Mapeamento:

| Variável do shadcn | Token semântico da skill (TOK-04) | Atenção |
| --- | --- | --- |
| `--background` / `--foreground` | `bg-page` / `text-primary` | |
| `--card` / `--card-foreground` | `bg-surface` / `text-primary` | |
| `--popover` / `--popover-foreground` | `bg-raised` / `text-primary` | menu, popover, select |
| `--primary` / `--primary-foreground` | `accent-solid` / `text-on-accent` | `primary` do shadcn **é** o acento da marca; nos tokens próprios, `primary` continua proibido para marca (TOK-03) |
| `--secondary` / `--secondary-foreground` | neutro de botão secundário (`bg-surface-hover` ou um degrau de neutro) / `text-primary` | |
| `--muted` / `--muted-foreground` | `bg-sunken` / `text-secondary` | `muted-foreground` precisa de 4,5:1 sobre `background`, `card` e `muted` (TOK-16) |
| `--accent` / `--accent-foreground` | `bg-surface-hover` / `text-primary` | `accent` do shadcn é o **realce de hover e item ativo de menu**, não o acento da marca |
| `--destructive` | `danger-solid` | texto sobre ele: `text-on-accent` ou a variável de primeiro plano da versão instalada |
| `--border` | `border-subtle` | borda decorativa de card e separador |
| `--input` | `border` | borda de controle, ≥ 3:1 (TOK-16) |
| `--ring` | `border-focus` | contraste contra tudo que o anel cruza (ACE-05) |
| `--chart-1` … `--chart-5` | paleta categórica validada | ordem e regras em `indicadores-e-graficos.md` e `dataviz` |
| `--sidebar`, `--sidebar-foreground`, `--sidebar-primary`, `--sidebar-primary-foreground`, `--sidebar-accent`, `--sidebar-accent-foreground`, `--sidebar-border`, `--sidebar-ring` | superfície do shell e os mesmos papéis acima | |
| `--radius` | raio de controle da família escolhida (TOK-21) | os outros raios derivam dele |
| `--shadow-2xs` … `--shadow-2xl` (sombras do `@theme` do Tailwind v4 que os componentes do shadcn usam) | níveis de elevação de TOK-34: `xs`/`sm` → `elevation-repouso-shadow`; `md` → `elevation-elevado-shadow`; `lg` → `elevation-flutuante-shadow` (apelido `shadow-overlay`); `xl`/`2xl` → `elevation-sobreposto-shadow` | Card em repouso, Popover, DropdownMenu e Toast em flutuante, Dialog e Sheet em sobreposto (EXP-43); no escuro, a superfície `-bg` do nível sobe por clareamento (TOK-35); nenhum `shadow-[…]` literal |

- **STK-11** · [DS] · P2. O shadcn não traz semânticas de status além de `destructive`. Acrescente `success`, `warning`, `info` (e `danger`) com as variantes `subtle`, `border`, `solid`, `text` de TOK-04, exponha-as ao Tailwind no `@theme inline` (`--color-success-subtle: var(--success-subtle)`) e crie as variantes correspondentes no Badge, no Alert e no Sonner. Em Tailwind v4, zere a paleta padrão no `@theme` (`--color-*: initial`) para que `bg-blue-600` não exista como atalho (GOV-01). *Verificar:* os selos de status da folha do sistema usam `bg-success-subtle text-success-text`, não `bg-green-100 text-green-800`.
- **STK-12** · [PR] · P2. **Cada direção de personalidade é um tema** (PER-08): um bloco de variáveis por direção (`[data-theme="bancada"]`, `[data-theme="balcao"]`), cada um com claro e escuro, aplicado na raiz (GOV-10); no starter, o atributo é `data-preset` (`src/proto/aparencia/presets.ts`). Trocar de direção no seletor da rodada troca o atributo, nunca o markup. A direção aprovada vira o tema padrão e as outras saem do build na promoção.

## 5. Ícones

- **STK-13** · [N casa] · P1. **Biblioteca de ícones é obrigatória** em todo protótipo e build: navegação, ações, status, vazios, campos com prefixo e alertas usam ícones de uma família instalada (ou carregada de CDN fixada, STK-05). Tela de app sem ícones onde a tarefa os pede (navegação primária, ações por linha, status) é achado. *Por quê:* foi uma das quatro queixas do usuário sobre os primeiros protótipos.
- **STK-14** · [N casa] · P2 (P1 quando o emoji é o único portador do sentido de um controle ou status). **Nunca emoji como ícone.** Emoji muda de desenho por sistema operacional, não herda `currentColor` nem o traço da família, não respeita a grade de tamanhos e é lido pelo leitor de tela pelo nome do emoji ("círculo verde grande"). Emoji só como conteúdo do usuário (chat, reação). *Verificar:* grep por caracteres de emoji em JSX, HTML e rótulos de status.
- **STK-15** · [PR] · P2. Uma família por produto (GOV-11), escolhida pela personalidade (PER-04): **Lucide** é o padrão com shadcn (traço uniforme, licença ISC); **Phosphor** quando a direção pede pesos (thin, light, regular, bold, fill, duotone) ou ativo preenchido; **Tabler** para acervo grande com versões em traço e preenchidas; **Iconoir** para traço mais leve e geométrico; **Iconify** como acesso a outros sets, conferindo a licença do set escolhido; set próprio só com desenho em grade e traço iguais aos da família. Licenças em `catalogo-de-fontes.md`.
- **STK-16** · [PR] · P3. O peso acompanha o tipo: traço de 1,5 px ao lado de texto 400 e de 2 px ao lado de 500–600, tamanho do ícone pela tabela de TOK seção 5; em Lucide, `absoluteStrokeWidth` mantém o traço ao mudar o tamanho. Estado **ativo preenchido, inativo em traço** (navegação, favoritos, filtros ligados) quando a família tem as duas versões (Phosphor `fill`, Tabler filled); em Lucide, que é só traço, marque o ativo por fundo, cor e peso, sem preencher à força.
- **STK-17** · [PR] · P2. **Ícones de status e de vazio fazem parte da direção**: um ícone por estado de cada objeto, ao lado do texto e da cor (ACE-22, LIS-05), registrado na tabela de estados junto da cor; um ícone (ou ilustração, se a direção tiver) por vazio, em tamanho maior que o de controle e de token próprio. A folha do sistema mostra os dois conjuntos (`assets/modelo-folha-do-sistema.md`).
- **STK-18** · [N] · P1. **Nome acessível sempre**: ícone decorativo ao lado de texto leva `aria-hidden="true"`; botão só com ícone tem `aria-label` com verbo + objeto (ACE-03). Quando o botão pode ser só ícone e o texto do tooltip são de TXT-11 e TXT-12; quando usar tooltip ou toggletip, de CAM-27.

## 6. Astro com React em ilhas, transições de página e `base`

- **STK-19** · [DS] · P2. Páginas e layouts são `.astro` estáticos; **só o que é interativo vira ilha React**, com a diretiva pelo momento em que precisa responder: `client:load` para o que se usa logo ao abrir (busca do topo, ações da linha, `<Toaster />`), `client:idle` para o que pode esperar o navegador ficar ocioso, `client:visible` para o que está abaixo da dobra (gráfico, comentários), `client:media` para o que só existe numa largura, `client:only="react"` para o que depende de `window` desde o início. No starter vale STK-29: uma ilha `client:load` por página. Componente sem diretiva é renderizado só no servidor e não responde a clique. *Verificar:* botão que não faz nada no protótipo porque o componente foi usado sem diretiva.
- **STK-20** · [PR] · P2. Contexto do React não atravessa ilhas: um gatilho e o seu conteúdo (Dialog, Sheet, Popover, DropdownMenu, Form) moram **no mesmo componente React**, hidratado inteiro. Estado compartilhado entre ilhas vai para a URL ou para um store pequeno (ex.: nanostores, a recomendação da documentação do Astro). Confira que um toast disparado de uma ilha aparece no `<Toaster />` da outra.
- **STK-21** · [DS] · P3. Integrações: `npx astro add react`, Tailwind pela integração oficial (v4 via plugin do Vite), shadcn pelo guia de instalação para Astro (alias `@/` no `tsconfig.json`, `components.json`). Tema aplicado por script inline no `<head>` antes do primeiro paint, sem flash (GOV-04).
- **STK-22** · [PR] · P2. O protótipo navegável usa **rotas reais** do Astro (no starter, `src/modulos/<id>/paginas/`, e detalhe por query string, `?id=`; em projeto existente, `src/pages/prototipos/<fluxo>/vN/...`), com `<a href>` entre telas, para que Voltar, recarregar e abrir em nova aba funcionem como no build. Estado simulado de criar, editar e excluir fica no navegador (PRO-09, "sem back-end"). Toda troca de página tem transição (MOV-26), com a mecânica de STK-26; em navegação de 100+ por dia ela é a mais curta (crossfade do conteúdo com o shell parado), nunca corte seco. Todo link e caminho respeita o `base` (STK-25).
- **STK-25** · [N casa] · P1. **Links e caminhos respeitam o `base`** do build, para que o protótipo e o app abram em qualquer subpasta (servidor da bancada, GitHub Pages, pasta de entrega, preview publicado). Em Astro, nada de `href="/prototipos/..."`, `src="/img/..."` ou `fetch("/fixtures/...")` com barra fixa: monte o caminho a partir de `import.meta.env.BASE_URL` com um auxiliar único (por exemplo, `url("prototipos/agenda/v1/")` em `src/lib/url.ts`, que junta as partes sem barra dupla, porque o `BASE_URL` pode ou não terminar em `/` conforme `base` e `trailingSlash`), usado nas páginas `.astro`, nas ilhas React e nos scripts. Arquivos de `public/` também passam pelo auxiliar. Em HTML autocontido (STK-05), use caminhos relativos. *Por quê:* um protótipo testado tinha `href="/prototipos/..."` fixo e quebrou ao ser servido numa subpasta. *Verificar:* grep por `href="/`, `src="/`, `fetch("/` e `url(/` em `src/`; configurar `base: "/teste/"` no `astro.config`, rodar `astro build && astro preview` e navegar por todas as rotas, imagens e fontes.
- **STK-28** · [N casa] · P1 · QUANDO (Astro com dados falsos, sempre no starter). **Tela pronta no HTML, com dados determinísticos.** A semente e a tela não leem `Date.now()`, `new Date()` sem argumento nem `Math.random()`: o tempo vem do relógio do protótipo (`agora()`, `useAgora()`, `nov()`) e o sorteio do gerador da semente (`colecao`). Nada de `window`, `localStorage` ou `matchMedia` durante o render; preferência que muda o HTML usa um gancho que vale o padrão no servidor (`useMovimentoReduzido`). *Por quê:* o servidor e o navegador precisam gerar o mesmo HTML; quando não geram, a hidratação falha e a tela pisca ou perde o dado da primeira pintura. *Verificar:* grep de `Date.now`, `new Date()` e `Math.random` em `src/modulos/`; o `navegar.mjs` acusa erro de hidratação no console.
- **STK-29** · [N casa] · P2 · QUANDO (protótipo sobre o starter). **Uma ilha `client:load` por página.** A tela da rota é a única ilha `client:load`; a casca hidrata em `client:idle` com `transition:persist`; peça pesada que só aparece depois de um clique (sheet, diálogo, quadro, gráfico rico) entra com `React.lazy`. *Por quê:* cada ilha `client:load` a mais disputa a hidratação com a tela e estoura a meta de troca de página (VER-36). *Verificar:* contar `client:load` em cada `.astro` de `paginas/`; o `medir.mjs` dentro das metas.
- **STK-26** · [DS] · P2. **Transições de página no Astro** (a regra de quando e qual é de MOV-26):
  - `<ClientRouter />` (de `astro:transitions`) no `<head>` do layout comum; com `fallback="animate"` (padrão), navegadores sem View Transitions ainda recebem a animação;
  - `transition:name` nos elementos compartilhados entre páginas (um nome por página; linha → cabeçalho do detalhe, miniatura → foto, botão da ação-chave → tela de confirmação) e `transition:animate` por relação (`fade` padrão, `slide` para sequência, `none` onde o elemento não deve mudar, ou animação própria com os presets de MOV-24);
  - `transition:persist` no shell e nas ilhas que guardam estado (sidebar recolhida, player, `<Toaster />`, carrinho), para que não remontem a cada página;
  - scripts: módulos empacotados rodam uma vez; código de configuração de página vai no evento `astro:page-load`; o tema é reaplicado em `astro:after-swap`, antes do paint, para não piscar (STK-21, MOV-27);
  - movimento reduzido: o `ClientRouter` desliga todas as animações de transição; para manter o crossfade curto do mapa de MOV-21, defina-o em CSS próprio;
  - alternativa sem JavaScript: View Transitions nativas entre documentos (regra CSS `@view-transition`), conferindo o suporte em `dispositivos-e-entrada.md`.

  *Verificar:* navegar pelas rotas do protótipo; o shell não pisca, a ilha persistida mantém o estado e o tema não volta ao padrão por um quadro.

## 8. Padrão detectável → correção

| Padrão detectável | Correção |
| --- | --- |
| Protótipo em HTML artesanal num projeto que tem dev server | Rota `/prototipos/` no stack real (STK-04) |
| HTML autocontido sem tokens, sem anatomia do shadcn ou sem ícones | Variáveis do tema, markup dos componentes, ícone de CDN fixada (STK-05) |
| Script de CDN com `@latest` ou só versão maior | Versão exata (STK-05) |
| Produto do zero sem DEC de stack | DEC "Astro + React em ilhas + shadcn/ui + Tailwind, trocável" (STK-02) |
| `div onClick` como menu, diálogo, abas ou combobox; toast ou tabela ordenável à mão | Componente do shadcn ou da biblioteca adotada (STK-06) |
| Segundo toaster, segunda tabela, segundo pacote de ícones | Uma biblioteca por papel (STK-07) |
| Biblioteca existente trocada sem pedido | Reverter; propor a troca como pedido à parte (STK-07, regra da casa 7) |
| Protótipo sem ícones, fontes ou imagens porque "não pediu para instalar" | Instalar dentro do projeto e registrar (STK-23) |
| Dependência nova sem linha na DEC ou no relatório; pacote global ou com chave paga instalado sem pedir | Registrar; para as exceções, perguntar antes (STK-23) |
| `className="bg-green-100 text-green-800"` em selo na tela | Variante `success` no Badge com tokens (STK-08, STK-11) |
| Texto animado, shader ou fundo de partículas em fila ou tabela | Mover para momento de personalidade, banner ou onboarding (STK-09, MOV-32) |
| Componente de expressão copiado sem licença registrada | Conferir e registrar a licença por item (STK-09) |
| `href="/..."`, `src="/..."` ou `fetch("/...")` com barra fixa em projeto Astro | Auxiliar com `import.meta.env.BASE_URL` (STK-25) |
| Layout Astro sem `<ClientRouter />`; sidebar ou toaster que remonta a cada página | `ClientRouter` e `transition:persist` no shell e nas ilhas com estado (STK-26) |

| Mola, layout ou gesto escritos à mão numa ilha React | Motion (STK-24) |
| Duas bibliotecas para o mesmo papel de movimento | Uma por papel (STK-07, STK-24) |
| Three.js, Rive ou Lottie carregados em toda página com `client:load` | Import dinâmico e `client:visible` só onde aparecem (STK-24) |
| Confete ou carimbo genérico como celebração padrão | Celebração do domínio; confete só como opção registrada (STK-24, MOV-30) |

| `--accent` do shadcn usado como cor da marca | `--primary` é a marca; `--accent` é hover (STK-10) |
| Direções da rodada como cópias da tela com outra cor | Um tema por direção em `data-theme` (STK-12) |
| Tela de app sem ícones na navegação, nas ações ou nos status | Família instalada (STK-13) |
| Emoji como ícone de status, ação ou navegação | Ícone da família + texto (STK-14) |
